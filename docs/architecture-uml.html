01 — Orientation

Two ways in, one way down

MealPlanner has two inbound surfaces — Blazor circuits on the LAN, and a loopback-only MCP endpoint a headless Claude drives — and they meet at InventoryService, which is the only thing in the assembly that opens a DbContext for inventory. Everything else in the app is arranged around that single door: a notifier so writes coming in one surface are seen by the other, and three interfaces that keep the parts calling out to a claude -p subprocess substitutable.

The rest of the plates take that shape apart. Read plate 1 for where things live, plates 2–5 for what the types are, and plates 6–8 for what actually happens over time.

02 — Domain

Two tables, and a lot of records that never land

Only InventoryItem and Recipe are entities. Everything else on plate 2 is an immutable record passing through: a proposal from a model, a request from a page, a result on its way back. The split matters because the records carry values that have not been normalized yet — a scanned line is still whatever a model read off a photograph until InventoryService clamps it.

03 — The choke point

Every mutation answers with a diff

No method on InventoryService returns void or signals a miss with an exception. They all return an InventoryChange, and ChangeKind covers the outcomes an exception would otherwise carry: NotFound, NameTaken, and Unchanged. That is what lets an MCP tool answer a string and a Razor page render a status line off exactly the same call.

Three responsibilities sit here and nowhere else: normalizing and clamping input (EF's [MaxLength] is not enforced and SQLite ignores TEXT lengths, so this is the trust boundary), retrying lost write races up to MaxUpsertAttempts, and publishing to the notifier once the write has actually landed.

Why the retry is eight and not one

An upsert is read-then-write against a case-insensitive unique index, so two writers on one name race. Every losing attempt flips branch — insert becomes update, update becomes insert — so a single retry is exhausted by three concurrent writers. Household members plus a headless Claude on the same names is this app's normal case, not its edge case.

04 — Ports and adapters

Three interfaces that keep a subprocess out of the tests

Each AI-backed feature is one interface and one implementation that shells out to claude -p. The interfaces exist for a specific, cashed-in reason: the test suite never spawns the CLI. Fakes stand in for the ports, and what is genuinely worth testing at the process boundary — BuildPayload for the stdin, ParseResults / ParseScan / ParseRecipes for the stdout — is internal static and pure.

All three implementations carry the same private shape: RunAsync → KillAndDrainAsync → Kill. The duplication is deliberate rather than factored into a base class, and the three bodies are meant to read identically.

05 — The background pipeline

Classification deliberately does not live in the service

A classification costs about three seconds and InventoryService sits on the path of every write, so the categorizer subscribes to the notifier instead of being called by the writer. Items appear in Other and move a moment later — and because that move is itself a write, it publishes like any other and open pages refresh themselves.

Structurally it is a producer–consumer pipeline: the notifier handler is the producer and returns immediately without awaiting anything, an unbounded single-reader Channel is the buffer, and the ExecuteAsync loop is the consumer. The batch window exists because eight names cost the same as one — spawning the process dominates.

06 — Collaboration

What actually happens, in order

The static plates hide the two things this app's design is mostly about: that a write is not finished until every open circuit has been told, and that nothing a model says reaches the database without a person confirming it. Plates 6 to 8 are the three flows where that shows.

07 — Catalogue

The patterns, and what each one is buying

Sixteen, listed with the concrete thing that would break without them rather than the textbook motivation.

PatternWhere it livesWhat it is buying here
Facade / choke point InventoryService One trust boundary for normalization and clamping, since [MaxLength] is not enforced by EF and SQLite ignores TEXT lengths. A page or tool touching the DbContext directly would bypass all of it.
Observer InventoryChangeNotifier A write arriving over MCP refreshes the kitchen's open tabs without a reload. Handlers are Func<InventoryChange, Task> so subscribers can await real work, and are subscribed as method groups because Unsubscribe matches on delegate equality.
Guarded concurrent fan-out PublishAsync + GuardedAsync A per-handler try/catch inside a Task.WhenAll. One torn-down circuit cannot starve the rest, and no task ever faults, so several dead subscribers cannot collapse into one AggregateException that hides all but the first.
Result object InventoryChange, ChangeKind Outcomes an exception would otherwise carry — NotFound, NameTaken, Unchanged — travel as data, so an MCP tool returns a sentence and a page renders a status line from the identical call.
Ports and adapters IIngredientClassifier, IRecipeGenerator, IReceiptScanner The suite never spawns the CLI. Fakes stand at the seam; the parsing and payload-building either side of the process boundary are pure static functions tested directly.
Strategy Program.cs registrations The same three seams read from the DI angle: one line swaps the implementation, and Enabled: false in config switches each feature off whole.
Producer–consumer IngredientCategorizer channel Keeps a three-second call off the path of every write. The notifier handler queues and returns at once, because every writer awaits the publish and anything slow there is a frozen Add button.
Batching window CollectBatchAsync Eight names cost the same as one — process spawn dominates — so a 400 ms window collects whatever arrives together, which is exactly the shape a confirmed receipt produces.
Factory IDbContextFactory, Func<InventoryService> A context per unit of work; and a singleton-registered factory that lets the singleton BackgroundService build a service per batch without capturing a scoped dependency.
Optimistic concurrency, bounded retry UpsertOnceAsync loop Read-then-write against a NOCASE unique index races. Every losing attempt flips branch, so the ceiling is eight rather than one — three concurrent writers on one name would exhaust a single retry and throw at the caller.
Options Three *Options classes Model, effort, timeout and ceilings live in appsettings.json. The divergences are meaningful: medium effort and 180 s for recipes against low and 90 s for classification.
Template shape, uninherited RunAsync / KillAndDrainAsync / Kill Three near-identical private methods rather than a base class. A broken pipe has to kill the child — disposing a handle does not — so every failure path funnels through one drain, and a fix landing in one body belongs in all three.
Adapter, protocol side InventoryTools Turns string-in / string-out MCP calls into service calls, catching the ArgumentException a UI guards against and answering a message instead.
Pure function over held state IngredientMatcher Static, no DI, no DbContext — a view over the items list the page already holds, not a second way into the database. Exact match autofills; near match only suggests.
Parameterized component IngredientCombobox Owns the widget — listbox, highlight, aria, blur dismissal. Each page owns what a match means. Ids derive from the Id parameter, which is the whole reason two can share a page.
Presentation model Row editor, receipt review Draft state lives in @code fields, never the DOM: a refresh from any writer replaces items, and a row whose category moved is re-keyed under another group and torn down. Focus is lost there; typed text must not be.

08 — Negative space

Patterns the code refuses on purpose

The absences are as load-bearing as the presences, and each one has been argued rather than overlooked.

  • No repository per entity, no unit-of-work abstraction IDbContextFactory is the whole of it. A repository layer over two tables in a one-household app would add an indirection that InventoryService already provides — and the service is where normalization and retry have to live anyway.
  • No retry loop and no publish in RecipeService Symmetry with InventoryService would be wrong. Recipes have no natural key and no unique index, so every save is a fresh insert that cannot collide, and no out-of-circuit writer touches them — the page that saved refreshes itself.
  • No base class for the three Claude adapters Their flag sets diverge where measurement said they should, and the shared private shape is small. The bodies are kept readable side by side instead of hoisted into an abstraction that would have to be parameterized on every difference.
  • No bool includeExactMatch on Suggest Inventory excludes the exact match because a row in that list can be arrowed onto, which would turn Enter from "add" into "fill". Recipes wants it and prepends ExactMatch itself. A flag would encode which page is asking into a pure function.
  • No classification inside the write path The obvious place for auto-categorization is UpsertAsync. It is not there because that method is on the path of every write and a classification takes seconds — the observer subscription is the whole reason the Add button stays responsive.
  • No chat surface on /recipes Knobs and cards. The generator is reached through a request record with an enum, three role lists and one clamped free-text brief — a shape a schema can pin — rather than an open conversation.
