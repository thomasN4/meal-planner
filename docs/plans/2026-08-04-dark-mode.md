# Plan: First-party dark mode — System / Light / Dark

Status: implemented (2026-08-04) — automated checks green, browser checks
deferred (see "What is not verified").
Scope: a dark palette following the OS preference by default, a persisted
three-state override, and an audit of every colour literal the app owns.
Explicitly **out of scope**: restyling the sidebar (it is brand navy in both
themes); per-user theme state (there is no auth and no per-user state anywhere
in this app); a light variant of the Blazor error chrome.

Closes #19.

## Context

The household browses with Dark Reader, which meant every visual decision here
had to survive a colour transformation we do not control and cannot test in CI.
That already cost real bugs. The suggestion list's highlight was `#e9ecef` on
`#fff` — fine normally, flattened by the extension to an 11/255 difference that
made arrow-key navigation unusable. The fix was an inset painted bar, on the
principle that *a remapper can rewrite a colour and cannot rewrite the fact
that one edge is painted*. The #18 row editor carries the same bar for the same
reason, and it was the one item from that PR's browser pass nobody had verified
under Dark Reader's dynamic mode.

Shipping our own dark theme lets the household turn the extension off for this
site. We then design for **two known palettes** instead of one known palette
plus an unpredictable filter.

The vendored Bootstrap is already **5.3.3**, which has native `data-bs-theme`
and sets `color-scheme: dark` for us under `[data-bs-theme=dark]`. So this was
never a Bootstrap upgrade — it is one attribute, a three-state control, and the
colour audit.

## Deliverables

### 1. `wwwroot/theme.js` — the single owner

Bootstrap 5.3 keys its dark palette off `[data-bs-theme=dark]` on `<html>`,
**not** off a `prefers-color-scheme` media query. There is therefore no
CSS-only spelling of "follow the system": resolving it needs script. Given that,
everything about the theme lives in one file, and `ThemeToggle.razor` is a view
over it that never decides the theme itself.

`window.mealPlannerTheme` exposes `get()` (the stored mode) and `set(mode)`.
An internal `apply()` resolves `system` through `matchMedia` and stamps
`document.documentElement`. It sets the attribute for light too, rather than
removing it, so the resolved theme is always readable off the DOM instead of
being "dark, or else absent".

Three things here are load-bearing:

- **The script is blocking, in `<head>`, before the stylesheets** (`App.razor`).
  Anything later — `defer`, end of `<body>`, a Blazor component that runs when
  the circuit connects — paints one frame of the wrong theme first. This is the
  reason the issue asked for an inline script; an external same-origin script
  achieves the same pre-paint timing while staying fingerprinted through
  `@Assets` and out of Razor's `@` escaping.
- **`Blazor.addEventListener('enhancedload', apply)`.** Enhanced navigation
  re-synchronises `<html>`'s attributes against the markup the server just
  sent, and the server sends no `data-bs-theme` — so without this, clicking a
  NavLink strips the attribute and snaps the page back to light. Wired from
  `DOMContentLoaded`, by which point `blazor.web.js` (the last element in
  `<body>`) has run.
- **`localStorage` access is wrapped in try/catch.** Private browsing throws on
  the getter, and "we cannot remember what you asked for" has a sensible
  answer already: follow the system.

If `enhancedload` ever proves unreliable, the fallback is to *also* persist a
cookie and stamp `data-bs-theme` server-side in `App.razor` for the explicit
light/dark cases, leaving JS responsible only for resolving `system`. That was
not done up front because it duplicates the source of truth for no benefit
unless the event actually misfires.

### 2. `Components/Layout/ThemeToggle.razor`

Three buttons — System / Light / Dark — in `MainLayout`'s top row, next to the
About link. **Three states rather than two**: "follows my OS" has to stay
reachable after someone has toggled once, and a two-way switch loses it
forever.

- `@rendermode InteractiveServer`, and the project's first `IJSRuntime`
  injection. `@using Microsoft.JSInterop` was already in `_Imports.razor`.
- `mode` starts at `system`, and `OnAfterRenderAsync(firstRender)` asks
  `theme.js` what is actually stored. The preference lives in localStorage,
  which the server cannot see, so the buttons can only learn it after the first
  render. Only the **active marker** arrives a beat late; the theme itself was
  stamped pre-paint.
- `aria-pressed` renders a **string**, never a bool. Blazor omits a false bool
  attribute, which would leave the unpressed buttons with no state at all.
  Breaking this turns all five tests red, not one.
- The current button carries the house **inset bar** plus `font-weight: 600`.
  Bootstrap's own `.active` on an outline button is a fill swap — state by
  colour alone — and this household has been bitten by that before.
- `Normalize` guards unknown values at both ends: localStorage is user-writable
  and outlives any rename of these three strings, and either end can be reached
  first.

### 3. The colour audit

Every literal the app owns became a `--bs-*` token, or was deleted:

- **`wwwroot/app.css`** — the template's `a { color: #006bb7 }`,
  `.btn-primary { #1b6ec2 }` and unused `.darker-border-checkbox` are **gone**.
  They are template blues with no dark counterpart, shadowing Bootstrap
  defaults that already move with the theme. The focus ring's inner stop was a
  literal `white`, which on a dark body is a bright ring rather than a halo; it
  is now `var(--bs-body-bg)`.
- **`Inventory.razor.css`** — the two inset bars take `--bs-link-color` (which
  lightens to `#6ea8fe` in dark, which is what a bar on a dark ground needs);
  the suggestion tint takes `--bs-primary-bg-subtle` (which drops to a
  near-black blue); muted text takes `--bs-secondary-color`, **not**
  `--bs-secondary` — the former is the muted-text token, the latter a fixed
  grey that would sit at ~3:1 on a dark ground.
- **`MainLayout.razor.css`** — the top row takes `--bs-tertiary-bg` and
  `--bs-border-color`. The sidebar gradient stays fixed: it is already dark, it
  is the only brand colour the app has, and NavMenu paints white on top of it.
  `#blazor-error-ui` already carried `color-scheme: light only` and was left.
- **`ReconnectModal.razor.css`** — background *and* `color`. A `<dialog>` takes
  its text colour from `canvastext`, so tinting only the background lands
  dark-on-dark.
- **`NavMenu.razor`** — `navbar-dark` (deprecated in 5.3) became
  `data-bs-theme="dark"` on that div, scoping the dark island explicitly. The
  rest of that stylesheet is untouched: its white icons live inside
  `background-image` data URIs, which cannot read custom properties at all, and
  flipping them would mean re-cutting each as `mask-image` + `currentColor` for
  no gain.

**The inset bars stay.** They were never a Dark Reader workaround specifically
— low contrast arrives from an extension, a washed-out laptop panel or
sunlight, and none of those can rewrite a painted edge. The comments explaining
them were rewritten rather than left: they narrated `#e9ecef on #fff`, and a
stale hex in a comment that no longer matches the code is worse than the
original problem.

### 4. Tests — `tests/MealPlanner.Tests/ThemeToggleTests.cs`

Five tests over a bare `BunitContext` rather than `PageHarness`: the toggle
touches no database, so a throwaway SQLite file would say nothing about it.
What does the work is bUnit's default **Strict** JS interop — the component's
only outside contact is `theme.js`, so Strict mode turns every unplanned call
into a failure, and that is the assertion surface.

One API trap worth recording: **`SetupVoid(identifier)` only matches a call
with no arguments.** `mealPlannerTheme.set` always carries one, so the bare
form let every real invocation fall through to Strict mode's exception. The
matcher overload (`SetupVoid(id, _ => true)`) is required; which argument
actually arrived is asserted at the call site instead.

Break-the-guard pass, per AGENTS.md — each of these was applied and confirmed
red before the suite was trusted green: removing the `OnAfterRenderAsync`
interop call; removing the `Normalize` fallback; dropping the `active` class;
rendering `aria-pressed` as a bool; and removing the `InvokeVoidAsync` on
click.

The existing page tests are untouched — `PageHarness` renders `Inventory` and
`Recipes` directly rather than through `MainLayout`, so the toggle is never in
their render tree and needs no `JSInterop` setup there.

## What is not verified

`dotnet build` (zero warnings), `dotnet test` (249 passing) and
`dotnet format MealPlanner.sln --verify-no-changes` are all green.

The browser half was **not** checked — this was written from a remote session
with no browser on the same machine. Outstanding:

1. **Enhanced navigation.** Home → Inventory → Recipes with Dark selected; the
   theme must survive every NavLink click. Highest-risk item, and the one with
   the documented cookie fallback above.
2. **No flash.** Hard-reload with Dark selected; no white frame.
3. **System mode is live.** Flip the OS theme with System selected; the page
   follows without a reload.
4. **The Inventory surfaces in real dark** — suggestion-list highlight and the
   open row editor, both bars still visible, **with Dark Reader disabled for
   the site**. This also finally closes the #18 leftover.
5. The toggle's own active marker settling correctly once the circuit connects.
